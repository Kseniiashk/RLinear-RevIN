# Предрегистрация проекта D3: RLinear и RevIN

**Курс:** Deep Learning  
**Команда:** Ксения Шкулева, Роман Светлов, Роман Шумилов  
**Статья:** Zhe Li, Shiyi Qi, Yiduo Li, Zenglin Xu. *Revisiting Long-term Time Series Forecasting: An Investigation on Affine Mapping* (2023, arXiv:2305.10721).

## 1. Статья и наша гипотеза

**Главная гипотеза статьи:** на сезонных многомерных рядах при достаточно длинной истории аффинное отображение с RevIN даёт точность долгосрочного прогноза, сопоставимую со сложными архитектурами.

Мы проверим это утверждение на ETTh1 и ETTm1. Ожидаем, что при одинаковой длине истории и одинаковом протоколе оценки лучшая из RLinear/RMLP будет отставать по MSE от лучшей из PatchTST и TimesNet не больше чем на 5%. Также посмотрим, какую часть результата даёт RevIN и насколько итоговые числа меняются из-за `drop_last=True` и длины входного окна.

**Гипотеза D3:** на ETTh1 при `H=96`, `L=336` вклад RevIN больше выигрыша от замены RLinear на PatchTST или TimesNet при общей RevIN. Критерий указан в разделе 4.1.

## 2. Что именно воспроизводим

Берём четыре строки из Table 2 версии статьи v2. Везде используется история длины `L=336`, прогнозируются все семь каналов, а качество измеряется по MSE и MAE. ETTh1 выбран потому, что на нём в статье лучше всего выглядит RLinear, а на ETTm1 уже выигрывает PatchTST, поэтому проверка не сводится к одному удобному для линейной модели датасету.

|---|---:|---:|---:|---:|---:|
| ETTh1 / 96 | .366 / .391 | .390 / .410 | .381 / .405 | .398 / .418 | .375 / .399 |
| ETTh1 / 336 | .420 / .423 | .441 / .441 | .431 / .436 | .493 / .468 | .439 / .443 |

В таблице указаны MSE / MAE из статьи. Используем стандартный для ETT хронологический сплит 12/4/4 месяца и отдельно стандартизуем каждый канал по train. Чекпоинт выбираем только по validation MSE. Для каждой конфигурации запускаем сиды 1024, 1025 и 1026, после чего показываем все три результата, среднее и выборочное стандартное отклонение.

Месяц означает 30 дней; шаг окна равен 1. Цели каждого окна целиком принадлежат соответствующему сплиту. Ошибки считаем в стандартизованной шкале по всем горизонтам и каналам. Сиды фиксируем для Python, NumPy и PyTorch.

RLinear и RMLP берём из репозитория RTSF. Для PatchTST, TimesNet и DLinear используем авторские реализации. Не все настройки из Table 2 опубликованы, поэтому до основных запусков фиксируем версии кода и полные конфиги. Если параметр в статье не указан, берём значение из официального скрипта модели. Это будет указано в отчёте. Для воспроизведения сохраняем опубликованные политики нормализации и eval drop-last; неизвестную политику явно отмечаем и используем полный test. Авторские и исправленные оценки показываем отдельно.

Сравниваем среднее по трём сидам с опубликованным числом: абсолютное относительное отклонение равно `abs(mean / paper - 1)`. Таблица считается воспроизведённой, если хотя бы 16 из 20 пар (модель, строка) отличаются от статьи не больше чем на 5% одновременно по MSE и MAE. Среди них должны быть хотя бы три из четырёх строк RLinear. Статья приводит округлённые результаты и не показывает разброс по сидам, поэтому более жёсткий порог сейчас трудно обосновать.

**Ожидание:** этот критерий выполнится, а лучшая из RLinear/RMLP на каждой строке будет находиться в пределах 5% по MSE от лучшей из PatchTST/TimesNet.

## 3. Запуск авторского кода

Команда из `script.md` не запустилась из-за неверного имени модели: вместо `Linear` в коде используется `RLinear`.

Мы заменили только имя модели и добавили `--num_workers 0`, чтобы запуск нормально работал на macOS. После этого RLinear на ETTh1 с `L=336`, `H=96`, batch size 128, learning rate 0.005 и сидом 1024 получила **MSE 0.3660 и MAE 0.3909**. В статье указаны 0.366 и 0.391. Весь процесс на Apple M2 Pro CPU занял 24.1 секунды. Это результат одного сида и исходного авторского протокола, в котором последний неполный тестовый батч отбрасывается.

Окружение пилота: macOS 26.2 arm64, Python 3.11.12, PyTorch 2.5.1, NumPy 1.26.4, pandas 2.2.3 и scikit-learn 1.5.2. Полные команды и stdout лежат в `pilot/`, версии библиотек указаны в `requirements-pilot.txt`.

Дополнительно провели пилотные проверки RLinear: отключение RevIN, изменение длины истории и сдвиг уровня. Результаты приведены в [`results/README.md`](results/README.md). Сравнение остальных архитектур ещё предстоит выполнить.

## 4. Что проверяем помимо таблицы

Все дополнительные сравнения проводим на ETTh1 при `H=96` и на тех же трёх сидах. Внутри каждой пары оставляем одинаковые окна, optimizer, batch size и правило выбора чекпоинта, чтобы менялся только интересующий нас фактор.

Для контролируемых сравнений: Adam, MSE, до 20 эпох, patience 5, постоянный LR. LR и batch size берём из закреплённого конфига модели и сохраняем внутри пары; для RLinear это 0.005 и 128, dropout 0.1. Все train-окна используются; validation/test без shuffle и без отбрасывания последнего батча. Метрики агрегируем по суммам ошибок и числу элементов. Для разных длин истории используем пересечение допустимых точек прогноза на каждом сплите и переобучаем модели.

### 4.1. Вклад RevIN

Для каждой из пяти архитектур сравним вариант с RevIN и без неё. Штатную нормализацию входного окна с обратным преобразованием отключаем в обеих ветках (включая TimesNet); в ветке с RevIN применяем общий блок ровно один раз, в другой — тождественное преобразование. Нормализации скрытых слоёв оставляем. Статистики RevIN считаем только по истории каждого канала, с обучаемым аффинным преобразованием и epsilon 1e-5. Сначала усредняем MSE по сидам, затем считаем снижение `100 * (1 - MSE_on / MSE_off)` для каждой модели.

Для гипотезы D3 медианное снижение по пяти моделям должно превышать `100 * max(0, 1 - min(MSE_PatchTST, MSE_TimesNet) / MSE_RLinear)` при общей RevIN. Дополнительно MSE RLinear должен быть не более чем на 5% выше лучшей из этих двух моделей.

**Ожидание:** RevIN снизит MSE хотя бы у трёх из пяти моделей, а медианное снижение будет не меньше 3%. Пилот RLinear уже выполнен; его результат учитываем отдельно от будущих запусков.

### 4.2. Потеря тестовых окон из-за `drop_last`

В RTSF тестовый loader использует `drop_last=True`. При `H=96` и batch size 128 из 2785 окон остаётся 2688, то есть последние 97 окон не участвуют в метрике. Для готовых чекпоинтов сравним оценку на полном test с оценкой на том же подмножестве, которое оставляет авторский loader. Ошибки будем суммировать по отдельным элементам, чтобы последний батч имел правильный вес.

Проверку выполняем на трёх чекпоинтах RLinear с RevIN: из одного упорядоченного прохода берём первые 2688 и все 2785 окон. Изменение равно `100 * (MSE_truncated / MSE_full - 1)`.

**Ожидание и результат пилота:** ожидали медианное абсолютное изменение MSE меньше 3%, получили 1.24%. Отбрасывание последних окон снизило ошибку на всех трёх сидах.

### 4.3. Длина истории

С RevIN сравним `L=96` и `L=336`. Чтобы сравнение было честным, в обоих случаях используем одни и те же точки начала прогноза: короткая история будет последними 96 значениями длинной истории, а будущие цели полностью совпадут.

**Ожидание:** более длинная история не будет одинаково полезна всем моделям. У большинства архитектур изменение MSE останется в пределах 5%; направление эффекта заранее не задаём, так как пилот RLinear уже не показал улучшения.

Первоначальная ставка для RLinear — снижение MSE минимум на 2% — не подтвердилась. Ожидание выше относится к ещё не выполненным сравнениям остальных архитектур; RLinear остаётся контрольным результатом.

## 5. Дополнительный эксперимент

Проверим устойчивость к постоянному сдвигу уровня. Для тестовых окон прибавим `+2` в стандартизованной шкале одновременно к истории и правильному ответу, не меняя scaler и веса модели. Основное новое сравнение проведём для PatchTST с RevIN и без неё, а уже полученные результаты RLinear оставим как контроль.

**Ожидание:** с RevIN MSE PatchTST изменится меньше чем на 3%, а без RevIN вырастет как минимум на 10%. Этот эксперимент проверяет только реакцию на постоянный сдвиг уровня, а не устойчивость к любому сдвигу распределения.

## 6. Бюджет и распределение работы

| Часть проекта | Количество запусков | Оценка на одной T4 |
|---|---:|---:|
| Авторский пилот | 1 запуск | меньше 5 минут |
| Основная таблица | 4 строки x 5 моделей x 3 сида | 8-20 часов суммарно |
| RevIN | 5 моделей x 2 режима x 3 сида | 2-6 часов |
| Проверка `drop_last` | повторная оценка готовых чекпоинтов | меньше 30 минут |
| Длина истории | 5 моделей x 2 длины x 3 сида | 2-6 часов |
| Сдвиг уровня | инференс PatchTST и RLinear | меньше 30 минут |

Запуски дольше пяти минут будем делать скриптами и логировать в MLflow. Для каждого запуска сохраняем конфиг, сид, версии кода, хеш данных, время и итоговые метрики. Если вычислительного бюджета не хватит, сначала уберём эксперимент со сдвигом уровня, затем сравнение длины истории, а после этого строку ETTm1 / 336. Для оставшейся основной таблицы всё равно сохраняем три сида.

Ксения отвечает за RLinear/RMLP, общую таблицу и текст. Роман Светлов отвечает за PatchTST, TimesNet и DLinear. Роман Шумилов отвечает за единый код загрузки данных, RevIN, проверку `drop_last` и сдвиг уровня. Перед основными запусками каждый участник проверяет хотя бы один чужой конфиг.

Суммарная предварительная оценка: 12–33 T4-часа без повторного учёта уже выполненного пилота. Замеров на T4 пока нет; оценки уточним после первого запуска каждой архитектуры и запишем изменения в журнал. При исключении строки ETTm1 / 336 исходный критерий 16/20 уже неприменим: результат отмечаем как частичное воспроизведение. Все отклонения фиксируем в [`DECISIONS.md`](DECISIONS.md).
